# cf 0.30 — Deal-Breakers D1–D10 as Testable Invariants

**Status:** Frozen at cf-authority 1.0 (0.30 release).
**Authority:** Pass 1 (Domain Purist disposition, §"§11 deal-breakers D1–D10"); OPEN-011.
**Design references:** `0.30-design.md` §2.5; `docs/design/0.30-decisions/pass-1.md` §"Six spec invariants"; `gate-evaluator-conformance-harness.md` §2.

These ten invariants define the non-negotiable contracts of cf-authority 1.0. An
implementation that violates any one of them is not a conforming cf-authority
implementation, regardless of test coverage or performance. They are the line between
"close enough" and "safe to ship."

Each entry has:
- A one-sentence statement of the deal-breaker.
- A one-sentence test predicate: the concrete, checkable condition.
- Enforcement kind: Spec-only | Statically checkable | Behaviorally testable.
- File:line citations for where the deal-breaker is codified.
- The conformance harness case(s) that cover it.

---

## D1 — Deterministic Pure Function

**Statement:** The gate evaluator MUST be a pure function of its inputs; given identical
inputs it MUST produce identical outputs, byte-for-byte, with no hidden global state, no
clock reads, and no store reads inside the call.

**Test predicate:** Run any `GateEvaluator.Evaluate` call three times with byte-identical
inputs; assert all three `EvaluateResult` values are byte-equal.

**Enforcement:** Behaviorally testable (Go test).

**Citations:**
- `docs/cf-authority-spec.md` §4.1 ("Determinism (deal-breaker D1)")
- `docs/design/0.30-decisions/pass-1.md:88` ("A **deterministic pure function** (D1)")
- `docs/design/0.30-design.md` §2.5 ("A deterministic pure function")
- `docs/design/0.30-completion/round-2/gate-evaluator-conformance-harness.md` §1 (GateEvaluator doc-comment)

**Conformance harness:** §5.2 Determinism check — each of the twelve cases is run three
times with identical inputs; all results must be byte-equal. Non-determinism is its own
failure category, independent of the case outcome. Cross-reference: `conformance/` cases 1–12 (determinism re-run applies to every case).

**Adversarial note:** This invariant is in the identity/auth surface area. Adversarial
case: inject a global counter or wall-clock read into the evaluator; assert the harness's
three-run determinism check catches it (result differs between run 2 and run 3 due to
counter increment or clock skew). The conformance harness enforces this by design.

## D2 — UNRESOLVABLE as First-Class Third State (Fail Closed)

**Statement:** When the evaluator cannot resolve an introducer locally (chain truncated,
missing grant message), it MUST return `Unresolvable` — never `Allow` and never `Deny` —
and the dispatcher MUST treat `Unresolvable` as `Deny` (fail closed).

**Test predicate:** Given an `EvaluateRequest` whose `ChainMessages` is truncated
mid-walk (one message replaced with an explicit missing-sentinel), assert the result is
`EvaluateResult{Decision: Unresolvable, MissingMessageID: <sentinel-id>}` — not `Allow`
and not `Deny`.

**Enforcement:** Behaviorally testable (Go test).

**Citations:**
- `docs/cf-authority-spec.md` §4.2 ("Fail-closed (deal-breaker D2)") and §4.6 ("UNRESOLVABLE handling")
- `docs/design/0.30-decisions/pass-1.md:90` ("UNRESOLVABLE handling (D2, D7)")
- `docs/design/0.30-design.md` §2.5 ("UNRESOLVABLE is a first-class third decision")
- `pkg/convention/delegation/trust.go:71-141` (six-variant Outcome enum; `ReadError` is the Unresolvable path)

**Conformance harness:** Case 9 — `store-read-error-fail-closed`. Chain is truncated;
the missing-sentinel for hop-2 grant is present. Expected: `Unresolvable` with
`MissingMessageID` set. The harness explicitly asserts: NOT `Allow` (catastrophic),
NOT `Deny` (loses upgrade path to approval flow). Cross-reference:
`gate-evaluator-conformance-harness.md` §2 row 9.

**Adversarial note:** This is identity/auth surface area. Adversarial case: an
implementation returns `Deny` (instead of `Unresolvable`) on a truncated chain. The
harness catches this because it asserts `Decision == Unresolvable` specifically. A
`Deny` result fails the case. This matters because `Unresolvable` preserves the upgrade
path: the dispatcher MAY synthesize a `delegation:request` future; a hard `Deny` closes
that path permanently.

## D3 — Cryptographic-Only Authority

**Statement:** Every chain link MUST be a signed binding of `(delegator_key,
delegate_key, scope, expiry)`; identities are keys, not names — no authority flows from
name matching, display-name aliasing, or claimed-but-unsigned identity assertions.

**Test predicate:** A `chain_to` predicate that references a principal by name rather
than by 32-byte Ed25519 public key MUST be rejected at parse time (parse error or
`Deny/predicate_unsatisfied`); a predicate that references the same principal by key
MUST be accepted.

**Enforcement:** Statically checkable (Go type check: `ChainToPredicate.pubkey` is
`bstr`, 32 bytes — no string-name field exists in the type).

**Citations:**
- `docs/cf-authority-spec.md` §2.1 ("`chain_to: <principal>` — by KEY, not by name")
- `docs/design/0.30-decisions/pass-1.md:50` ("by KEY, not name — naming-as-authority is a vector")
- `docs/design/0.30-decisions/pass-1.md:109` ("Six spec invariants #6: Cryptographic-only identity")
- `docs/design/0.30-design.md` §2.4 ("`chain_to` by KEY, not name. Naming-as-authority is a vector.")
- `docs/design/0.30-completion/round-2/gate-evaluator-conformance-harness.md` §1 (`RootPrincipal ed25519.PublicKey` — key, not string)

**Conformance harness:** Implicitly covered by cases 1, 2, 3 (all use `RootPrincipal`
as a raw Ed25519 public key; any implementation that resolves by name rather than key
would fail to anchor correctly on mismatched-name fixtures). No dedicated case; the
structural enforcement is in the Go type system (`ChainToPredicate = {kind: "chain_to",
pubkey: bstr}` — no name field).

**Static check:** `grep -n 'ChainToPredicate' docs/cf-authority-spec.md` must show
`pubkey: bstr` (32 bytes); no `name: tstr` field exists. This is depguard-enforceable:
no code path in `cf-authority/` may resolve a chain using a string name as the trust
anchor.

## D4 — Verified-Chain Discipline

**Statement:** Authorization decisions MUST be made only on the verified chain of signed
messages; the scope payload of any grant is tainted (a free claim) until it has been
verified against the chain walk and intersected against the parent's verified scope.

**Test predicate:** Given a `delegation:grant` message whose claimed `op_pattern` is
wider than its parent's verified `op_pattern`, assert the evaluator returns
`Deny/scope_widening` — the claimed (but unsigned-relative-to-parent) scope is never
accepted at face value.

**Enforcement:** Behaviorally testable (Go test, conformance case 8).

**Citations:**
- `docs/design/0.30-decisions/pass-1.md:104` ("Six spec invariants #1: Verified-chain-trust")
- `docs/design/0.30-decisions/pass-1.md:105` ("Six spec invariants #2: Independent re-derivability")
- `docs/cf-authority-spec.md` §1.5 ("Sub-grant scope is set-intersection on each axis")
- `pkg/convention/delegation/trust.go` (chain walker; scope intersection enforced at each hop)

**Conformance harness:** Case 8 — `scope-widening-rejected`. Hop-2 claims `ready:*`
but hop-1 only grants `ready:claim`. Request is `ready:done`. Expected: `Deny/scope_widening`.
Cross-reference: `gate-evaluator-conformance-harness.md` §2 row 8.

## D5 — Reserved-Op Floor

**Statement:** The ten reserved operations (`disband | evict | admit | grant | revoke |
delegation-grant | delegation-revoke | delegation-accept | member-roster | compaction`)
carry a protocol-level minimum depth/level floor that NO convention declaration and NO
parent grant can lower; convention authors are not in the trusted computing base.

**Test predicate:** A convention declaration that declares `level: 0` on
`delegation-grant` MUST cause the evaluator to return `Deny/reserved_op_floor` — the
declaration-author's override is not honored.

**Enforcement:** Behaviorally testable (Go test, conformance case 11).

**Citations:**
- `docs/cf-authority-spec.md` §4.5 ("Reserved-op floor (deal-breaker D5)")
- `docs/design/0.30-decisions/pass-1.md:54` ("Reserved-op protocol floor (D5)")
- `docs/design/0.30-design.md` §2.4 ("Reserved-op protocol floor. The ten reserved ops…")
- `cf-protocol/internal/reserved-ops.go` (L1 authoritative list; see OPEN-003)
- `docs/design/0.30-completion/round-2/gate-evaluator-conformance-harness.md` §2 row 11

**Conformance harness:** Case 11 — `reserved-op-floor`. Convention declaration claims
`level: 0` on `delegation-grant`. Expected: `Deny/reserved_op_floor`. This defeats
Adversary attack 4 (convention author self-exempts via gate declaration).
Cross-reference: `gate-evaluator-conformance-harness.md` §2 row 11.

**Adversarial note:** This is identity/auth surface area. Adversarial case: an
implementation honors the convention-author's `level: 0` override on `delegation-grant`
and returns `Allow`. The harness case 11 catches this — expected result is `Deny/reserved_op_floor`.

**Delegation extent cross-reference:** The depth-1 cap for reserved ops is sub-claim (c)
of the delegation extent invariant: "Reserved ops cap at depth 1." See
`docs/cf-authority-spec.md` §0 ("Delegation Extent Invariant") for the full three-part
invariant and rationale. The depth cap is distinct from D5's level floor — D5 forbids
lowering the level requirement; sub-claim (c) adds a separate depth ceiling of 1 for
reserved ops regardless of granted level.

## D6 — Clamping Order: Owner Ceiling > Parent Grant > Convention Declaration

**Statement:** The authority composition order is fixed and one-directional: owner policy
overrides parent grant overrides convention declaration. No lower layer may widen above
the layer above it.

**Test predicate:** Given an `OwnerPolicy` that blanket-denies a convention:op, a parent
grant that permits it, and a convention declaration that also permits it, assert the
evaluator returns `Deny/owner_ceiling`.

**Enforcement:** Behaviorally testable (Go test).

**Citations:**
- `docs/cf-authority-spec.md` §3.2 (`OwnerPolicy` with `BlanketDeny []string`)
- `docs/design/0.30-decisions/pass-1.md:54` ("Owner ceiling > parent grant > convention declaration — the clamping order is fixed (D6)")
- `docs/design/0.30-design.md` §2.4 ("Owner ceiling > parent grant > convention declaration")
- `docs/design/0.30-completion/round-2/gate-evaluator-conformance-harness.md` §1 (`OwnerPolicy` doc-comment: "Composes one-directionally: owner > parent > declaration (deal-breaker D6)")

**Conformance harness:** `DenyReason = "owner_ceiling"` is a stable code in the
conformance contract (`docs/cf-authority-spec.md` §3.4). No dedicated conformance case
exists yet for D6 in the twelve canonical cases — the `OwnerPolicy.BlanketDeny` path is
exercised implicitly. A dedicated case is a test-gap (see §Gap below).

**Test gap:** No canonical conformance case directly asserts D6 clamping with a
blanket-deny policy. Proposed: `owner-blanket-deny` — `OwnerPolicy.BlanketDeny = ["ready:*"]`;
grant and convention both permit `ready:claim`; assert `Deny/owner_ceiling`.

**Delegation extent cross-reference:** The clamping order "owner ceiling > parent grant >
convention declaration" is the mechanism that makes sub-claim (a) of the delegation extent
invariant safe: an owner may delegate any action scope they hold precisely because the
clamping order prevents any delegate from widening scope above what the owner granted. See
`docs/cf-authority-spec.md` §0 ("Delegation Extent Invariant") for the full three-part
invariant. D6 ensures the "may delegate any action scope" claim does not become a
privilege-escalation vector.

## D7 — No Forever Grants

**Statement:** Every grant MUST have a mandatory `until` expiry field; grants without
expiry MUST be rejected at parse time; re-approval auto-extends `until` bounded by 30d;
no mechanism exists to create a permanent grant.

**Test predicate:** Attempt to parse a `delegation:grant` message whose `GrantPayload`
Capability tuple omits field 5 (`until`); assert the parser returns an error before
the grant reaches the evaluator.

**Enforcement:** Statically checkable (Go type/parse enforcement) + Behaviorally
testable (parse-time rejection test).

**Citations:**
- `docs/cf-authority-spec.md` §1.1 ("Field 5 (`until`) is mandatory. There are no 'forever' grants. Grants without `until` MUST be rejected at parse time.")
- `docs/design/0.30-decisions/pass-1.md:17` ("**Mandatory.** No 'forever' grants (D7 deal-breaker)")
- `docs/design/0.30-decisions/pass-1.md:70` ("**`--persist <ttl>` widens up to a 30d cap.** **No 'forever' grants** (D7 deal-breaker)")
- `pkg/convention/delegation/grant.go` (202 LOC; `Scope`, `MaxDepth`, `AllowRedelegation` fields; `until` enforcement)

**Conformance harness:** Case 4 — `expired-mid-chain`. Hop-2 `until` < CurrentTime by
1ns. Expected: `Deny/expired`. This tests the evaluator-side enforcement (expired grants
are rejected). Parse-time enforcement of missing `until` is a separate static check —
the conformance harness fixture format constraint (§5.4) mandates that all fixture chains
include `until`.

## D8 — Walk Every Dispatch

**Statement:** The dispatcher MUST re-walk the full delegation chain to the human root on
every dispatch; it MUST NOT trust cached scope claims or grant summaries from
session-create time; the cache may store the walk's `(input, output)` pair but never the
scope claim in isolation.

**Test predicate:** A dispatcher that returns `Allow` for a second dispatch in a session
without re-walking the chain (e.g., by trusting "session-grant says X") is in violation;
assert that revoking a mid-chain grant between two dispatches causes the second dispatch
to return `Deny/revoked` even if the first dispatch succeeded.

**Enforcement:** Behaviorally testable (integration test: revoke mid-chain between two
dispatches; assert second dispatch fails).

**Citations:**
- `docs/design/0.30-decisions/pass-1.md:1` ("walks **every dispatch** (caches the walk's input/output, never the scope claim)")
- `docs/design/0.30-decisions/pass-1.md:94` ("Five attacks the model defeats #1: Self-grant via session-creator laundromat — defeated by re-walking chains every dispatch")
- `docs/design/0.30-design.md` §2.3 ("The dispatcher re-walks to the human root on every dispatch — it never trusts 'session-grant says X.'")

**Conformance harness:** Case 5 — `revoked-mid-chain`. Fresh revocation view names hop-2
child key. Expected: `Deny/revoked`. This verifies that mid-chain revocation is honored
(not just root-level). The "walk every dispatch" property is enforced by the dispatcher
not by the evaluator itself — the evaluator is stateless, and the dispatcher must ensure
it re-presents the current chain on each call.

**Test gap:** No conformance case directly simulates two sequential dispatches with a
revocation between them. This requires a dispatcher-level integration test, not just an
evaluator unit test. A test-gap item is appropriate if the dispatcher has no such
integration test.

## D9 — Identity-Revoked Cascade

**Statement:** When a chain root posts `identity:revoked`, the entire delegation chain
anchored to that root is invalidated; revocation cascades down the chain automatically
via the revocation view, not only at the root.

**Test predicate:** Given a revocation view that contains a revoke message naming a
mid-chain key (not just the root), assert the evaluator returns `Deny/revoked` for any
request whose chain passes through that mid-chain key.

**Enforcement:** Behaviorally testable (Go test, conformance case 5).

**Citations:**
- `docs/design/0.30-decisions/pass-1.md:72` ("Revocation: owner posts `delegation:revoke`…cascade follows the chain (D9)")
- `docs/design/0.30-design.md` §2.7 ("Revocation: owner posts `delegation:revoke` on the identity campfire; cascade follows the chain.")
- `docs/cf-authority-spec.md` §4.2 ("Dispatchers treat `Unresolvable` as `Deny`") and §3.4 (`DenyRevoked`)
- `pkg/convention/delegation/trust.go:282-303` (DoS-hardened revoke set; revocation enforcement)

**Conformance harness:** Case 5 — `revoked-mid-chain`. Fresh `RevocationView` names
hop-2 child key. Expected: `Deny/revoked`. The case specifically falsifies "implementations
that revoke only on chain-root, not mid-chain." Cross-reference: `gate-evaluator-conformance-harness.md` §2 row 5.

**Adversarial note:** Identity/auth surface. Adversarial case: an implementation only
checks revocation against the chain root. Case 5 fixture has a revocation on hop-2 (not
the root). The harness expects `Deny/revoked`; an implementation that skips the mid-chain
revocation check returns `Allow` (catastrophic) or `Deny/predicate_unsatisfied` (wrong
reason code). Both fail the case.

## D10 — Depth ≤ 2 Default

**Statement:** The default maximum delegation chain depth is 2 (human → agent →
ephemeral worker); reserved ops are capped at depth 1; deeper chains require explicit
owner widening through the approval flow.

**Test predicate:** A three-hop delegation chain (`root → intermediate → sub-agent →
worker`) against a default depth-2 policy MUST return `Deny/depth_exceeded`.

**Enforcement:** Behaviorally testable (Go test, conformance case 6).

**Citations:**
- `docs/cf-authority-spec.md` §1.5 ("Hard depth limit: 2")
- `docs/design/0.30-decisions/pass-1.md:38` ("Hard depth limit: 2. This rejects sysop-delegation v0.1 §9.2's depth-3 default")
- `docs/design/0.30-design.md` §2.3 ("Hard depth limit: 2. The deployment shape is `human → agent → ephemeral worker`.")
- `pkg/convention/delegation/trust.go:24` (depth cap enforcement in existing chain walker)

**Conformance harness:** Case 6 — `depth-exceeded`. Three-hop chain against depth limit
2. Expected: `Deny/depth_exceeded`. This tightens sysop-delegation v0.1 §9.2 (which
specified depth 3 as the default). Cross-reference: `gate-evaluator-conformance-harness.md` §2 row 6.
