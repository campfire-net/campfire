# cf 0.30 — Cross-Line Critical-Fix Risk Register

**Status:** Active. Required before Stage 1 begins (per design v2 §7, OPEN-030).

**Purpose:** Track every fix that must land on the 0.19 line and be forward-ported to 0.30. Without this register,
fixes drift between lines and the two lines diverge silently. Each row states the surface touched, the owner, the
risk of the fix itself, and the rollback plan.

**Scope:** Only fixes that must ship on BOTH 0.19 and 0.30. Features go into 0.30 only. This register is for the
critical-fix set that 0.19 requires to stay production-safe during the 0.30 build period (~23 weeks).

## Risk Register

### FIX-1 — Rekey concurrency: evict-rekey DKG share loss (MB1)

| Field | Value |
|---|---|
| **Audit ID** | MB1 |
| **Severity** | CRITICAL |
| **Bet** | Statefulness |
| **Surface** | `pkg/protocol/evict.go` · `rekeyAfterEvict()` · DKG share distribution under concurrent evicts |
| **Owner** | campfire-agent (protocol implementer) |
| **0.19 status** | OPEN — tagged CRITICAL in code comment; not yet patched |
| **0.30 status** | OPEN — fix must land in 0.19 first; forward-port to 0.30 Stage 1 |
| **Target date** | Before Stage 1 (0.30 build begins) |

**What could break:** Two concurrent `Evict` calls on the same campfire race through `rekeyAfterEvict`. The second
caller reads a membership snapshot that the first is mid-updating. The DKG re-run distributes shares to a member
set that is inconsistent with the store. Result: one or more remaining members hold an invalid threshold share;
subsequent sends by that member fail with a signature verification error that looks like a corrupt campfire. Data
loss risk: messages accepted between the two evicts may be unreadable by the member whose share was invalidated.

**What the fix touches:** `rekeyAfterEvict` needs a per-campfire write lock. The lock scope is the entire
read-membership → run-DKG → write-new-campfire-ID sequence. The fix must not hold the lock across network I/O
(DKG is local, so this is achievable). The evict path is one of five places the membership set is mutated; the
lock must be the same primitive used by admit, leave, and disband to avoid deadlock.

**Rollback plan:** If the lock implementation introduces a regression (e.g., evict deadlock under admit+evict
contention), revert to the pre-patch state by removing the lock. The pre-patch state is racy but at least
fail-open. The regression is detectable via the `members_test.go` concurrent-admit-leave tests before the commit
lands. CI gate: `go test ./pkg/protocol/... -race -count=3` must pass.

### FIX-2 — Rekey concurrency: UpdateCampfireID silent divergence (MB2)

| Field | Value |
|---|---|
| **Audit ID** | MB2 |
| **Severity** | CRITICAL |
| **Bet** | Statefulness |
| **Surface** | `pkg/protocol/evict.go` · `UpdateCampfireID` · `epoch_secrets` field |
| **Owner** | campfire-agent (protocol implementer) |
| **0.19 status** | OPEN — tagged CRITICAL in code comment |
| **0.30 status** | OPEN — forward-port to 0.30 Stage 1 alongside FIX-1 |
| **Target date** | Before Stage 1 (same window as FIX-1) |

**What could break:** `UpdateCampfireID` is called after a successful rekey to persist the new campfire ID and
group key. If `epoch_secrets` is missing from the store record (e.g., it was never written because an earlier rekey
was interrupted), the function silently succeeds but writes a diverged campfire ID. The member whose store has the
diverged ID can no longer send or read — every message it signs references the wrong campfire key. This divergence
is silent: no error is returned, no log line is written, and the member continues accepting the campfire as valid.

**What the fix touches:** `UpdateCampfireID` must return an error (not silently succeed) if `epoch_secrets` is
absent. The caller in `rekeyAfterEvict` must handle the error — either retry or return it to the caller as a
hard failure. This is a two-line change in the happy path but requires updating every call site of
`UpdateCampfireID` to handle the new error return. CI gate: add a test that deliberately omits `epoch_secrets`
before calling `UpdateCampfireID` and asserts an error is returned.

**Rollback plan:** If error propagation from `UpdateCampfireID` breaks a caller that was previously relying on
silent success (e.g., a test that fakes a rekey without populating epoch_secrets), revert the error-return change.
The pre-patch silent-success behavior is a worse failure mode, but a known one. Before rollback, audit all
call sites to confirm none legitimately call `UpdateCampfireID` without epoch_secrets populated.

### FIX-3 — Billing stub replacement (StubVerifier)

| Field | Value |
|---|---|
| **Audit ID** | T5 |
| **Severity** | CRITICAL |
| **Bet** | Statefulness |
| **Surface** | `pkg/x402/x402.go` · `StubVerifier` · `cmd/cf-functions/main.go` |
| **Owner** | campfire-agent (hosted service operator) |
| **0.19 status** | OPEN — `StubVerifier` is wired to `/api/payment` in production right now |
| **0.30 status** | OPEN — 0.30 will ship `cf-functions` with real verifier; same fix needed on 0.19 line before 0.30 ships |
| **Target date** | Before 0.30 Stage 4 (reference deployment binaries); sooner on 0.19 |

**What could break:** `StubVerifier` accepts any `PaymentProof` with a syntactically valid `TxHash` field without
verifying the on-chain transaction. Any client that knows the API format can submit fake payment proofs and receive
`CapIncrease` (1,000 additional messages). In production this means unlimited message cap bypassing at zero cost.
The stub is intentional for the integration path but must not remain in production past the first commercial
customer.

**What the fix touches:** Replace `StubVerifier{}` in `main.go` with a real on-chain verifier (Base USDC
transaction lookup). The verifier interface (`x402.Verifier`) is already defined; only the implementation changes.
The fix is isolated to `pkg/x402/` (the new verifier) and `cmd/cf-functions/main.go` (wire it in). The stub
remains in `x402_test.go` for integration test use. No protocol surface change; no convention schema change.

**Risk of the fix:** The real verifier introduces a network call to a blockchain RPC on every payment request.
If the RPC is slow or unavailable, payment verification fails and customers cannot increase their cap. The fix
must include a timeout (< 5s) and a clear error response distinguishing "payment not found" from "verifier
unavailable." The `StubVerifier` must be retained for tests but must not be compile-time wirable to `main.go`
without a build tag (e.g., `//go:build stub`).

**Rollback plan:** Revert `main.go` to `StubVerifier{}`. The rollback is one-line and deploys in under 5 minutes
via the existing CI/CD pipeline. The rollback accepts the billing-fraud risk temporarily; it does not break any
user functionality. Monitor for unusual cap-increase request volume during the transition.

### FIX-4 — Health probe: real liveness check (T6)

| Field | Value |
|---|---|
| **Audit ID** | T6 |
| **Severity** | CRITICAL |
| **Bet** | Topography |
| **Surface** | `cmd/cf-functions/main.go` · `handleHealth()` · child process liveness check |
| **Owner** | campfire-agent (hosted service operator) |
| **0.19 status** | OPEN — health handler returns 200 if child process exists, even if child is deadlocked |
| **0.30 status** | OPEN — same logic; same fix must land on both lines |
| **Target date** | Before 0.30 Stage 4; sooner on 0.19 (production risk now) |

**What could break:** The current `/api/health` handler checks child process existence (`cmd.Process != nil`) but
not child process responsiveness. A deadlocked or panic-looping child will cause `handleHealth` to return HTTP 200
while the service is functionally down. Load balancers and the Azure deployment health check both trust this
endpoint. Result: a deadlocked instance continues receiving traffic; the deploy pipeline reports the service
healthy when it is not; customers get timeout errors with no operator alert.

**What the fix touches:** `handleHealth` and `waitReady` already poll the child's `/health` endpoint during
startup (`waitReady` at `main.go:316`). The production handler must do the same: proxy a liveness probe to the
child's `/health` on every request and return 503 if the child does not respond within a short timeout (< 2s).
This is a ~20 LOC change in `handleHealth`. The child's `/health` is already implemented (cf-mcp serves it);
only the parent's forwarding logic needs updating.

**Risk of the fix:** If the child is slow to respond (e.g., under load), the parent's `/api/health` returns 503
and the load balancer may pull the instance from rotation unnecessarily. Mitigation: use a generous timeout (2s)
and only report unhealthy after N consecutive failures (e.g., 3). This avoids transient load spikes causing
false-negative health reports.

**Rollback plan:** Revert `handleHealth` to the process-existence check. This restores the pre-patch behavior
(always 200 while child process is alive) and eliminates false-negative risk. The rollback accepts the dead-
instance-routing risk. If rolling back, open an incident and schedule a re-fix within the same sprint.

### FIX-5 — Identity: in-flight identity primitive changes

| Field | Value |
|---|---|
| **Audit ID** | I1, I9, I13 (see note) |
| **Severity** | load-bearing (each individually) |
| **Bet** | Identity |
| **Surface** | `pkg/protocol/` · `pkg/convention/delegation/` · `cf home revoke` command |
| **Owner** | campfire-agent (protocol implementer) |
| **0.19 status** | OPEN — `identity:revoked` tag has zero receivers; admission does not check revocation; revocation lives only in delegation convention, not base protocol |
| **0.30 status** | RESOLVED by design (§2.7 revocation cascade, §2.3 re-anchor, cf-authority L3) — but the design must not land piecemeal on 0.19 |
| **Target date** | 0.19: no partial identity changes without operator approval. 0.30: Stage 3 (cf-authority critical path). |

**What could break:** I1, I9, and I13 form a revocation triangle — each is individually a load-bearing gap, and
fixing one without the others reopens the gap. A partial fix (e.g., adding a receiver for `identity:revoked` on
0.19 without updating admission to check revocation) can create a false sense of correctness: `cf home revoke`
produces a tag that is consumed somewhere, but revoked identities can still be admitted to new campfires.

**This is the highest-risk cross-line item.** The 0.30 design closes all three gaps atomically in cf-authority
(Stage 3). On the 0.19 line, the constraint is: **make no partial changes to the identity revocation chain**.
Any in-flight identity primitive change on 0.19 must be reviewed against all three gaps before merging.

**What the fix touches (0.19 constraint):** No code changes to I1/I9/I13 on 0.19 without an explicit operator
decision that the partial fix is net-positive. The risk register records this as a blocking constraint, not a
pending fix.

**What the fix touches (0.30):** cf-authority Stage 3 closes the triangle. The GateEvaluator conformance harness
case 5 (revoked-mid-chain) and case 9 (store-read-error-fail-closed) verify the fix end-to-end.

**Risk of the fix (0.30):** cf-authority is the Stage 3 critical path (~6 weeks). If cf-authority slips, the
revocation triangle remains open on 0.30 as well. Mitigation: Stage 3 is sequenced after Stage 2 (cf-convention
machinery), which provides the evaluator interface. Do not start partial cf-authority work in Stage 2.

**Rollback plan (0.19):** The rollback plan for a prohibited partial fix is: do not merge it. If a partial fix
is mistakenly merged on 0.19 and discovered to reopen the gap, revert the commit and re-evaluate the full
triangle fix. For 0.30: if cf-authority Stage 3 blocks, defer the named consumers that require gate predicates
(dontguess spend cap, rd write authorization) rather than shipping a partial evaluator.

## Forward-Port Protocol

When a critical fix lands on 0.19:

1. **Tag the commit** with `[cross-line: campfireagent-f3a0]` in the commit message.
2. **Open an rd item** for the 0.30 forward-port immediately, blocking Stage 1 if not yet ported.
3. **Update this register** — change `0.30 status` from OPEN to IN-PROGRESS or DONE.
4. **Verify the forward-port** compiles and passes `go test ./... -race` on the 0.30 branch before closing the
   port item.

The register is authoritative for cross-line tracking. The orchestrator checks this document at Stage 1 kickoff
to confirm all critical fixes are either ported or explicitly deferred with operator approval.
