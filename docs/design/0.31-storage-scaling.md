# v0.31 Storage Scaling — Bucket Key, Compact Reply-Chain Policy, Migration Safety

**Status:** Design spike — accepted decisions, ready for implementation items.
**Item:** campfireagent-7ce
**Parent:** campfireagent-5a7e (v0.31 storage-scaling swarm)
**Scope:** `cf-protocol/internal/transport/fs/`. Hosted (`aztable`) and other transports are out of scope.
**Forcing function:** freeso body-cf write profile — ~1 Hz writes sustained for 24 h+ on a single persistent campfire. ~86,400 messages/day, growing without bound until the operator compacts. The existing flat `messages/` directory degrades on stat/readdir cost long before retention pressure becomes interesting.
**Hard constraints:**

- Public API surface (`Client.Send`, `Client.Read`, `Client.Subscribe`, `Client.Await`) is **off limits**. None of these methods change shape.
- Wire format is **frozen** at v0.30 (CBOR field IDs locked, including `Antecedents=5` on the message envelope). No new wire fields.
- `campfire:compact` event semantics are **fixed** by `docs/protocol-spec.md` §Compaction (append-only, signed, `supersedes` is the authoritative list, `retention` is a local hint).

The three resolved decisions follow. Every section closes with a **testable assertions** block — downstream impl agents write tests directly from those assertions without needing to re-read the discussion.

## §1 — Decision 1: Bucket Key

### §1.1 Today

`fs.Transport.WriteMessage` (cf-protocol/internal/transport/fs/fs.go:166) writes:

```
<campfire-dir>/messages/<19-digit-unix-nanos>-<message-id>.cbor
```

`fs.Transport.ListMessages` (cf-protocol/internal/transport/fs/fs.go:336) calls `os.ReadDir`, lex-sorts entries, and decodes. The 19-digit zero-padded nanosecond prefix makes lex-sort equivalent to chronological order on a single writer. Multi-writer ties break on message-id suffix — non-deterministic across writers, but stable per-message.

This file *is* the source-of-truth ordering for the fs transport. The store layer (`internal/store`) may reproject; the transport returns messages in lex order of filename.

### §1.2 Options considered

| Option | Layout | Lex-sort preserves chronological order? | Operator inspection | Whole-bucket-delete locality | Dir cost @ 1 year × 1 Hz |
|---|---|---|---|---|---|
| **A. Timestamp-prefix (UTC day)** | `messages/YYYY-MM/DD/<19-nanos>-<id>.cbor` | **Yes** — `YYYY-MM` lex-sorts as date, `DD` lex-sorts as date, nanos-prefix lex-sorts as time. `walk-buckets-in-lex-order, lex-sort-within-each` is identical to flat lex-sort by nanos. | `ls messages/` → 12 months × N years. `ls messages/2026-05/` → 31 days. Human-meaningful. | High: `compact --before 2026-05-01T00:00:00Z` is `rmdir messages/2026-04/` etc. `--keep-last N` only helps when N straddles a clean day boundary. | 12 × 365 = 4,380 month-dirs + day-dirs over a year. Inode-cheap. |
| **B. Hash-prefix** | `messages/<id[0:2]>/<id[2:4]>/<19-nanos>-<id>.cbor` | **No** — buckets shuffle order. Reconstructing chronological order requires reading every bucket and merging by the in-filename nanos prefix. O(buckets × log entries) merge cost on every `ListMessages`. | `ls messages/` → 256 dirs of opaque hex. Useless for humans. | Low: each bucket holds a uniform-random slice of all-time messages. Whole-bucket delete is never aligned with `--before` or `--keep-last`. | 256 × 256 = 65,536 dirs eagerly, regardless of message count. Spends inodes for cold campfires. |
| **C. Sequence-window** | `messages/<floor(seq/1000)>/<19-nanos>-<id>.cbor` | Partial — requires a monotonic per-campfire sequence number that the fs transport does **not** currently maintain. Adding it means either a new persisted counter file (write hot path takes a lock) or post-hoc renumbering from filenames (defeats the point). | OK once you know N. | High when `--keep-last N` aligns to window size; arbitrary `--before` requires per-file decisions. | Manageable, but the sequence-counter file becomes the new write-throughput bottleneck and a new failure mode (counter rollback on crash mid-write). |

### §1.3 Decision: **Option A — UTC-day timestamp-prefix**

```
<campfire-dir>/messages/<YYYY-MM>/<DD>/<19-nanos>-<message-id>.cbor
```

- Bucket bounds are **UTC midnight to midnight**. Wall-clock skew is the writer's `time.Now()` (same source as the existing 19-nanos prefix), so a bucket's residents are guaranteed monotonic-on-this-writer.
- `YYYY-MM` is `time.Now().UTC().Format("2006-01")`; `DD` is `time.Now().UTC().Format("02")`. Both zero-padded; both lex-sortable.
- The 19-digit nanos prefix on the leaf filename is **kept unchanged**. This preserves the inside-bucket lex-sort invariant and avoids any wire-format pressure.

### §1.4 Why A over B and C

1. **Total order is the load-bearing invariant.** `ListMessages` callers (most notably the protocol's reply-chain walkers and the cf-conventions dispatcher polling loop) depend on chronological output. Option B breaks it, forces a merge step on every read, and the merge cost grows linearly with retention. Option A keeps the existing lex-sort property *literally identical*: read buckets in lex order, lex-sort within each bucket, concatenate — the result is byte-identical to today's flat lex-sort.
2. **Compact locality.** `cf compact --before <ts>` is the dominant operator command for persistent campfires. With Option A, "before 2026-05-01" becomes `os.RemoveAll(messages/2026-04/)` plus per-file deletes inside one straddle-day bucket. Whole-bucket removal is O(1) per directory (one syscall); per-file deletes are O(N). The retention=`discard` case under §985 of the protocol spec gets cheap. Option B never aligns; Option C only aligns when the operator happens to compact at sequence-window boundaries.
3. **Operator-inspection ease.** Operators *will* read these directories during incidents (we've watched them do it). `ls messages/2026-05/16/` produces a human-meaningful answer. `ls messages/a3/` does not.
4. **Distribution under freeso load.** ~86,400 msgs/day in one day-bucket. ext4/XFS handle 100k entries in a single dir without the `O(n²)` slowdown that the *current* flat layout will hit at year 1 (~31M files). 100k/day is well inside the comfort zone for any post-2010 filesystem. The new pressure point — directory-block rebalancing within a 100k-entry leaf — is bounded per day; today's pressure is unbounded.
5. **Dir creation cost.** A bursty-then-quiet campfire (the more common case than freeso) creates one `YYYY-MM/DD/` pair per *active* day, not per message. Cold campfires create zero new dirs after initial.

### §1.5 Trace through ListMessages

The required modification to preserve callers' semantics:

```
old: ReadDir(messages/) → sort → decode
new: ReadDir(messages/)
     → filter dir entries (skip the legacy flat *.cbor files during migration window)
     → sort YYYY-MM dirs lex
     → for each: ReadDir, sort DD dirs lex
       → for each: ReadDir, sort *.cbor lex, decode
```

Because the lex orderings nest exactly (`YYYY-MM < YYYY-MM`, then `DD < DD`, then `nanos-id < nanos-id`), the *concatenated* output is in the same total order as the legacy flat lex-sort. **This is the testable invariant** (see §1.7).

### §1.6 Edge cases

- **Empty day directories left after compact.** `RemoveAll(messages/YYYY-MM/DD/)` is fine; if it leaves an empty `YYYY-MM/`, future writes naturally re-create siblings. Pruning empty month dirs is a best-effort post-step, not load-bearing.
- **Clock skew producing out-of-order writes within a single writer.** Already possible today (CLOCK_REALTIME may step backwards). The 19-nanos prefix still sorts deterministically; the day bucket may be "wrong" by one boundary. We accept this — same behavior as today, and the protocol's antecedents-DAG is the authoritative causal order anyway.
- **A message written at exactly 23:59:59.999999999 UTC.** Lands in today's bucket. The next write at 00:00:00.000000001 lands in tomorrow's. Total order is preserved across the boundary because tomorrow's `YYYY-MM/DD` lex-sorts after today's.
- **Push-subscriber inbox layout.** Push subscribers receive raw `copyFile(src, dst)` of the message bytes. The `dst` filename is set to `filename` (the leaf `<19-nanos>-<id>.cbor`) — see fs.go:184. The subscriber inbox is **not** day-bucketed in v0.31. Inboxes are short-lived and small; bucketing them adds complexity without payoff. **This is an explicit non-scope item.**

### §1.7 Testable assertions (for downstream impl items)

A1. After N writes spread across two days, `ListMessages` returns the same `[]Message` (in the same order) as a parallel flat-layout transport receiving the same writes.

A2. `WriteMessage` creates exactly `messages/<YYYY-MM>/<DD>/<19nanos>-<id>.cbor` and nothing else (except `MkdirAll` ancestors).

A3. Given N writes on day D, `len(ReadDir(messages/<YYYY-MM>/<DD>/))` == N. Given zero writes on day D', `Stat(messages/<YYYY-MM>/<DD'>/)` == not exist.

A4. `ListMessages` on a freshly-initialized campfire with zero messages returns `(nil, nil)` — same as today.

A5. **Order-preservation regression:** seed a campfire with K messages whose nanos timestamps span >=3 distinct UTC days; assert `ListMessages` output IDs are in the same order as `sort(filenames-flattened-then-lex)`.

A6. `WriteMessage` with `time.Now()` mocked to step backwards across a day boundary still produces a file under the new (earlier) bucket and the old bucket retains its file; no panics, no overwrites.

A7. A directory entry that is neither `.cbor` nor a 7-character `YYYY-MM` nor a 2-character `DD` dirname is silently ignored by `ListMessages` (forward-compat with hypothetical sidecar files).

## §2 — Decision 2: Compact Reply-Chain Policy

### §2.1 The constraint

Compaction is **append-only** by protocol-spec.md §Compaction:

> Compaction does not delete messages. It appends a `campfire:compact` event that declares which messages are superseded.

The protocol *already* has a tombstone-by-event-log model. Message A is "removed" by a signed `campfire:compact` event whose `supersedes` list contains A's ID. Any reader that wants the post-compaction view filters using the union of all `supersedes` lists (this is exactly what `protocol/await.go:listCompactedMessageIDs` does today).

What v0.31 adds: under retention=`discard`, the **on-disk** file `messages/.../A.cbor` may be removed. The event-log entry (the signed compact message) remains. The question is what happens to a still-resident message B whose `Antecedents` list contains A.

### §2.2 Reply-chain field inventory

Grepped `cf-protocol/` and `cf-conventions/` for fields that carry message-ID references. **Findings:**

- **`Antecedents []string`** on the L1 message envelope (CBOR field id 5, cf-protocol/internal/message/message.go:48). This is the *only* wire-level inter-message reference. **Frozen.**
- **`Supersedes []string`** in the `CompactionPayload` JSON body of a `campfire:compact` message (cf-protocol/internal/store/store.go:1097). Application-layer; lives inside the message payload bytes.
- **`target_message`** — convention-layer argument name (cf-conventions/cf-convention/declarations/operator-revoke.json, swarm-coordination conventions). At wire time, the dispatcher places the referenced ID into `Antecedents`. There is no separate wire field.
- **`fulfills`** — a reserved tag (`TagFulfills = "fulfills"`). Its semantic referent — the future being fulfilled — lives in `Antecedents`. The tag is a marker; the link itself is via Antecedents.
- **`MessageID` (`message_id` JSON)** in `cf-conventions/cf-convention/dispatcher.go:216` — internal request-routing struct, never serialized to the wire.

**Conclusion:** at the wire layer there is exactly one inter-message-reference field, `Antecedents`. Every "reply", "fulfillment", "target", and convention-argument-of-type-`message_id` resolves to `Antecedents` at serialization time. This means a single policy on Antecedents covers everything.

### §2.3 Options considered

| Option | Behavior when B.Antecedents ⊇ {A} and A is being compacted | Signature integrity | Spec alignment |
|---|---|---|---|
| **R — Refuse** | `cf compact` fails when any non-supersede-listed message references the supersede set. Operator must either re-issue compact with extended `--supersedes` or accept rejection. | Preserved (no rewrites). | Adds a new error to the compact command. Protocol-spec says nothing about this — silent under §Compaction. |
| **D — Drop reference** | Rewrite B's bytes with A removed from Antecedents. | **Broken.** B's signature covers `Antecedents`. Rewriting invalidates the signature → no reader can verify B → equivalent to corrupting B. |
| **T — Materialize a tombstone file** | After deleting A.cbor under retention=discard, write a tiny `A.tombstone` placeholder so B's "load by ID" resolves to "this was here, compacted by event X". | Preserved (B unchanged). | Adds a new on-disk artifact not specified by protocol-spec. New code path. |
| **N — No special action (current behavior)** | After deleting A.cbor, B remains valid. Readers that want to dereference B.Antecedents look up A via the existing `awaitCompactedMessageIDs` machinery (or any caller-side equivalent) and resolve to "compacted, see event E". | Preserved. | Matches what the spec already says — superseded messages are excluded from default reads; the event log is the source of truth. |

### §2.4 Decision: **Option N (no policy) + explicit specification of the `campfire:compact` audit event content.**

Rationale:

1. **The protocol already solves this.** Spec §Compaction says compaction is event-log-based and append-only. The signed `campfire:compact` message *is* the tombstone — collectively, the union of `supersedes` across all compaction events tells any reader "this ID was compacted by event E at timestamp T by signer S." Adding a parallel filesystem tombstone duplicates that authority and introduces a second source of truth (the on-disk `.tombstone` file vs. the in-log event), which we will then have to keep consistent across transports.

2. **Refusing (R) inverts the operator's command.** Persistent campfires *will* have multi-hop reply chains. Refusing compact-the-old when the new references it forces the operator to compact more and more, defeating the bound. Option R also can't work cross-transport: a hosted store can't statically verify Antecedents references at compact time without scanning the entire still-resident message set.

3. **Drop (D) is excluded by the signature model.** Not negotiable.

4. **Tombstone files (T) cost an inode per compacted message** and a write per compact-step, doubling the on-disk write amplification of compact under retention=discard. With 86,400 msgs/day, a year-long compaction would create ~31M `.tombstone` files in their day buckets. The event log already carries this information for free.

**Therefore:** v0.31 does *not* add a new file-system policy. The existing semantics — `campfire:compact` is signed, append-only, and authoritative — are sufficient. What v0.31 **does** add is a pinned specification of what the audit event must contain (§2.5), so downstream readers don't have to guess.

### §2.5 `campfire:compact` audit-event content (pinned)

The event already exists; v0.31 pins its content as a **named, testable contract**. The payload remains as defined in `internal/store/store.go:1095` and protocol-spec.md:993, and v0.31 adds **no new fields** (wire freeze):

```
campfire:compact payload {
  supersedes:        [message-id, ...]   # complete list of IDs being superseded (REQUIRED, non-empty)
  summary:           bytes               # human/agent-readable description (REQUIRED, may be empty bytes for retention=discard with no new state)
  retention:         "archive" | "discard"  # local-storage hint (REQUIRED)
  checkpoint_hash:   hex-string          # SHA-256(sorted({id}|{hex(sig)})) over Supersedes (REQUIRED, 64 hex chars)
  bytes_superseded:  int64               # sum of len(payload) over Supersedes; 0 = "not provided" (OPTIONAL, validated when nonzero)
}
```

Envelope-level invariants v0.31 reaffirms (these are not new — but downstream impl tests must assert them):

- **Tag set:** the message MUST carry tag `campfire:compact` and SHOULD NOT carry any other reserved-namespace tag.
- **Antecedents:** the compaction event's `Antecedents` SHOULD contain the ID of the most-recent superseded message — establishing the causal boundary (protocol-spec.md:1002).
- **Signer:** signed by a member holding the `full` role (protocol-spec.md:977, §1014).
- **Coverage:** `supersedes` is a snapshot of intent. v0.31 explicitly does **not** require `supersedes` to include dependents of any included message. Dangling Antecedents references *out of* the resident set are normal and resolved by the union-of-compaction-events lookup.

#### Range encoding

The pinned format keeps `supersedes` as an explicit ID list (no range compression). Rationale: enumerated IDs are checkpoint-hashable; ranges are not without an authoritative ordering. The hashable property is load-bearing for `checkpoint_hash` integrity.

### §2.6 What the FS transport actually does at compact-time

For `retention=discard`:

1. The compacting client constructs the `campfire:compact` message (per §2.5).
2. After the compact event is durably written via the existing message-write path, the fs transport MAY delete on-disk files for IDs in `supersedes`. Deletion is best-effort: failure to delete a single file is logged and does not block other deletes.
3. The compact event itself (a regular message) is written into the appropriate day bucket like any other message. It is **never** itself deleted.

For `retention=archive`:

- The fs transport does not delete any on-disk file. Readers exclude superseded IDs from default reads at the protocol layer (already implemented).

### §2.7 Testable assertions

R1. With messages A (day-1) and B (day-1) where `B.Antecedents = {A}`, sending a `campfire:compact` with `supersedes=[A]` and `retention=discard` succeeds. Post-compact: A's file is removed from its day bucket, B remains on disk byte-identical (signature verifies), the compact event itself is on disk in its day bucket.

R2. After R1: `ListMessages` returns B and the compact event but not A. Default-filtered reads at the protocol layer exclude A; a caller that asks for B and walks B.Antecedents into A receives a "compacted by event E" indication from `awaitCompactedMessageIDs` (existing behavior).

R3. A compact event with empty `supersedes` is invalid and rejected by the existing validator (`ValidateCompactionBytes`-adjacent checks). Negative test.

R4. A compact event with `bytes_superseded` set MUST match the sum of `len(payload)` across superseded messages (existing validation, retained).

R5. Two compact events that both include the same ID in `supersedes` are both valid; readers union their `supersedes` lists (existing behavior, kept under the new bucket layout).

R6. **Cross-day compact:** `cf compact --before <ts>` removes all *.cbor files in fully-covered day buckets via `os.RemoveAll(messages/YYYY-MM/DD/)` plus per-file removes inside the straddle bucket. The directory `messages/YYYY-MM/DD/` is `Stat`-not-exist for fully-covered days afterward.

R7. `compact:performed` is **not** a separate event type. The single `campfire:compact` event IS the audit record. A downstream test that searches for `compact:performed` as a tag MUST fail and be corrected to look for `campfire:compact`.

## §3 — Decision 3: Migration Safety Contract

### §3.1 Surface

A new subcommand `cf migrate-store` lives in the public campfire repo's `cmd/cf` package. It operates on a single campfire directory: `<base-dir>/<campfire-id>/` (or the path-rooted equivalent). It migrates `messages/*.cbor` from the legacy flat layout to the day-bucketed layout described in §1.

The migration command is **the only writer** that touches the on-disk message layout during its run. The public `Client.Send` / `Client.Read` / `Client.Subscribe` / `Client.Await` API surface does **not** change. The fs transport's `WriteMessage` is **dual-read, single-write** for one transitional release (§3.4).

### §3.2 Live-write semantics: lockfile

Three options were considered:

1. **Quiesce required.** Operator must stop all writers, run migration, restart. Simple, but operationally hostile for hosted persistent campfires and for the freeso pattern where a body-cf has 1 Hz writes from a long-running automaton. Rejected.
2. **Copy-on-write.** Migration takes a snapshot, builds the new layout under `messages.new/`, and live writes go to *both* old and new locations during the build. Complex (write amplification, divergent-write reconciliation), too heavy for a one-shot tool. Rejected.
3. **Lockfile + dual-read.** Migration acquires an exclusive flock on `<campfire-dir>/.migrate.lock`. While the lock is held, `WriteMessage` blocks acquiring a *shared* flock on the same file (cheap, no other contention). Reads continue without taking the lock. Total writer-stall is bounded by `migrate-store` runtime (linear in current file count + one rename). **Chosen.**

#### Lockfile semantics

- Path: `<campfire-dir>/.migrate.lock`. Created by either side on first access (it is a zero-byte file; only the flock state matters).
- Migration holds `LOCK_EX` for the entire migration run.
- `WriteMessage` acquires `LOCK_SH` per call. Multiple writers can hold `LOCK_SH` concurrently; the migration's `LOCK_EX` waits for all of them.
- `ListMessages` does **not** take a lock. Reads are best-effort during migration and may observe a mid-migration state (some messages under flat, some under buckets). §3.4 makes this safe by dual-reading.
- On Windows (no flock): the implementation falls back to `O_EXCL` create of `<campfire-dir>/.migrate.lock.pid` and writers spin/back-off for up to 30 seconds before erroring. Migration-on-Windows is an acceptable degraded mode; not the primary deployment target.

### §3.3 Atomic-swap mechanism

The migration is built around a **two-rename atomic swap**:

```
1. Acquire LOCK_EX on .migrate.lock.
2. Detect layout (see §3.5).
3. If already bucketed → release lock → exit 0 idempotent.
4. Create <campfire-dir>/messages.new/ (mkdir 0700).
5. For each *.cbor in <campfire-dir>/messages/:
     parse 19-nanos prefix → derive <YYYY-MM>/<DD>
     mkdir -p messages.new/<YYYY-MM>/<DD>
     copy bytes (NOT rename — we want messages/ intact until swap)
6. Run verification (§3.6) on messages.new/ against messages/.
7. Rename messages/      → messages.old/   (atomic on POSIX).
8. Rename messages.new/  → messages/       (atomic on POSIX).
9. Release LOCK_EX.
10. Sleep (or wait for explicit operator command) and then remove messages.old/.
    (Default: keep messages.old/ until next successful migration run or
    until operator runs `cf migrate-store --finalize`.)
```

Steps 7–8 are the swap. POSIX guarantees both `rename(2)` calls are atomic *individually*. The window between them (a few microseconds) is the only point at which `<campfire-dir>/messages/` does not exist as a directory. Writers blocked on `LOCK_SH` see the post-swap state when they wake. Readers that happen to call `os.ReadDir(messages/)` during the window receive `ENOENT` and retry — `ListMessages` MUST handle `ENOENT` as "no messages, nil error" (it already does for first-write campfires: fs.go:341).

#### Mid-swap interruption recovery

| State found on restart | Meaning | Recovery |
|---|---|---|
| `messages/` exists, no `messages.new/`, no `messages.old/` | Either pre-migration or post-finalize. | Re-run migration; idempotence check (§3.5) skips if already bucketed. |
| `messages/` and `messages.new/` both exist, no `messages.old/` | Crash between steps 5 and 7. | Delete `messages.new/` and re-run. Source `messages/` is untouched. |
| `messages.old/` exists and `messages/` exists | Crash between steps 8 and 10 (or finalize not yet run). Both contain the same messages (one in old layout, one in new). | Inspect `messages/`: if bucketed → all good, operator can `--finalize` to remove `messages.old/`. If flat → step 8 didn't happen; rename `messages/` to `messages.discard/`, rename `messages.old/` to `messages/`, and re-run migration. |
| Only `messages.old/` exists, no `messages/` | Crash *during* step 8 (between the two renames). Vanishingly rare window. | Rename `messages.old/` → `messages/` and re-run migration. |
| Only `messages.new/` exists, no `messages/`, no `messages.old/` | Crash *during* step 7 (between the two renames). Equally rare. | Rename `messages.new/` → `messages/` and re-run migration. |

**No state is unrecoverable.** The recovery rule is mechanical: prefer the directory that actually contains the messages; the migration tool re-runs idempotently.

### §3.4 Dual-read writer (transitional)

For one release (v0.31), the fs transport's `ListMessages` **dual-reads**:

1. Walk day-bucketed layout (§1.5).
2. Walk top-level flat `*.cbor` entries in `messages/` (legacy).
3. Merge by lex-sort of leaf filename.

`WriteMessage` **always** writes to the new bucketed location post-v0.31 — there is no dual-write. This is safe because:

- A pre-migration store has only flat files; dual-read finds them in step 2.
- A post-migration store has only bucketed files; dual-read finds them in step 1 (step 2 is empty).
- A mid-migration store (between steps 5 and 7) still has *all* messages in the flat `messages/` dir; `messages.new/` is not where `ListMessages` reads. Mid-migration writers add new files to flat `messages/` *during the dual-write step* — see correction in next paragraph.

**Correction:** to avoid mid-migration writes landing in the (about-to-be-swapped-out) source dir, `WriteMessage` consults the migration lock state at write time. If migration is in progress (LOCK_EX held), `WriteMessage` blocks on `LOCK_SH` and waits. This eliminates the mid-migration-write problem entirely; writes that land during the lock wait go to the new bucket layout (because by the time they get `LOCK_SH`, the swap has happened). The dual-read remains for genuine legacy stores that have not been migrated yet.

In v0.32, dual-read is removed; only the bucketed path is supported.

### §3.5 Idempotence detection

Order of checks at `migrate-store` start (after acquiring `LOCK_EX`):

1. If `<campfire-dir>/messages/` does not exist → exit 0 (nothing to migrate; transport will create it on first write).
2. List entries of `messages/`:
   - If **all** entries are dirnames matching `^\d{4}-\d{2}$` (with internal `^\d{2}$` dirs) → store is already bucketed → exit 0.
   - If **all** entries are `*.cbor` files (flat legacy) → proceed with migration.
   - **Mixed state** (some bucket-dirs, some flat files): exit with `MigrationInconsistentLayoutError` listing the offending entries. Operator must clean up manually. (Mixed state should only occur after a failed migration where recovery was incorrect; the recovery rules in §3.3 prevent producing it.)
3. (Optional) If a marker file `messages/.layout-version` exists, read it: `v0.31-bucketed-utc-day` means already migrated. The marker is **not authoritative** — the directory-shape check in step 2 is. The marker is a hint for human operators inspecting the directory.

The migration writes `messages/.layout-version` containing the literal bytes `v0.31-bucketed-utc-day\n` as the **last** step inside the lock (between step 8 and step 9 above). It is a hint, not a guard.

### §3.6 Verification step

Before the swap (between steps 6 and 7 in §3.3):

1. **Count check.** `count(messages/*.cbor)` (legacy flat) MUST equal `count(messages.new/**/*.cbor)`. Mismatch → abort, leave `messages.new/` for operator inspection, return `MigrationCountMismatchError`.
2. **Spot-check.** Sample `min(64, count)` random files from `messages/`. For each, locate the corresponding file in `messages.new/<YYYY-MM>/<DD>/<same-leafname>` and assert byte-identical content. Any mismatch → abort, return `MigrationByteMismatchError` with the offending IDs.
3. **Leaf-name preservation.** No file is renamed during migration. Only the parent directory changes. This is the load-bearing invariant for the spot-check.

`MigrationByteMismatchError` is a hard stop. The operator must investigate; the migration tool does not auto-recover from byte divergence (it suggests filesystem corruption, not migration bugs).

### §3.7 Members / push-subscribers / campfire.cbor preservation

**Explicit, load-bearing:** the migration MUST NOT read, write, or rename any of:

- `<campfire-dir>/members/` and any `*.cbor` inside.
- `<campfire-dir>/push-subscribers/` and any `*.txt` inside.
- `<campfire-dir>/campfire.cbor`.
- `<campfire-dir>/.cf/` (if present — operator identity material).

The migration command is strictly scoped to `<campfire-dir>/messages/`, its sibling `messages.new/`, and the lockfile `.migrate.lock`. A defense-in-depth assertion at the top of the migration code path asserts that all other sibling entries are stat-identical (mtime, size, inode) before and after the migration. Mismatch → `MigrationCorruptedOtherStateError`, hard fail.

### §3.8 Testable assertions

M1. **Flat → bucketed:** seed `messages/` with N files at varying nanos prefixes spanning ≥3 UTC days; run migrate-store; assert `messages/` now contains only `YYYY-MM/DD/` directories, no flat `*.cbor`, and `messages.old/` contains the original N files; assert `ListMessages` returns the same N messages in the same order before and after.

M2. **Idempotence:** running migrate-store twice on the same store is a no-op on the second run. Second-run exit code is 0; no `messages.old.2/` or similar is created.

M3. **Mid-swap kill simulation:** simulate crash between rename(messages → messages.old) and rename(messages.new → messages). Assert recovery rule from §3.3 makes the store consistent on next migrate-store run.

M4. **Live write under lock:** start migration on a campfire with 100k seeded messages; concurrently spawn 10 goroutines calling `WriteMessage`. Assert (a) all 10 writes succeed, (b) all 10 land in the new bucketed layout, (c) the migration completes without error, (d) post-migration `ListMessages` returns 100k + 10 messages in correct order.

M5. **Count mismatch:** mid-migration, externally delete a file from `messages.new/`. Assert migration aborts at verification with `MigrationCountMismatchError`; `messages/` is untouched; `messages.new/` remains for inspection.

M6. **Byte mismatch:** mid-migration, externally truncate a file in `messages.new/`. Assert migration aborts at verification with `MigrationByteMismatchError`.

M7. **Members untouched:** seed `members/`, `push-subscribers/`, `campfire.cbor`; run migration; assert byte-identical content and stat-identical mtime/inode/size for all of those after the run.

M8. **ENOENT during swap window:** with a synthetic delay injected between the two renames, call `ListMessages` from another goroutine; assert it returns `(nil, nil)` (not an error). Equivalent: cf-protocol/internal/transport/fs/fs.go:341 already handles this for the first-write case.

M9. **Already-migrated detection without marker:** delete `messages/.layout-version` from a migrated store, re-run migrate-store, assert idempotent no-op (directory-shape detection takes precedence).

M10. **Already-migrated detection with marker:** intentionally introduce a marker file claiming `v0.31-bucketed-utc-day` on a still-flat store. Assert migrate-store ignores the marker and runs anyway because the directory shape is flat.

M11. **Public API unchanged:** assert no exported symbol in `cf-protocol/protocol` was added, removed, or had its signature changed by v0.31. (Run `go doc` diff against v0.30 tag; CI gate.)

M12. **Wire-format unchanged:** the existing wire-format-freeze test (test/demo/20-wire-format-freeze.sh) passes against the v0.31 tree.

## §4 — Cross-cutting: what v0.31 does **not** touch

- `Client.Send`, `Client.Read`, `Client.Subscribe`, `Client.Await` — no signature changes, no semantic changes.
- CBOR field IDs and the wire envelope — frozen.
- Hosted (`aztable`) and HTTP transports — out of scope. Each transport defines its own physical layout; this design is the fs transport's plan.
- Push-subscriber inbox layout — not bucketed; same `<inbox>/<leafname>.cbor` model as today.
- `cf-conventions` and convention declarations — no schema change. `target_message` and `fulfills` continue to compose down to `Antecedents` at wire time.
- The `campfire:compact` event schema — no new fields, no removals. v0.31 only **pins** the existing fields as a named contract.

## Appendix A — Why we did not introduce a new `compact:performed` event

The orchestrator's task prompt mentioned `compact:performed` as the signed audit record. The protocol spec already has exactly this in the form of `campfire:compact` (protocol-spec.md §989). Introducing a separate `compact:performed` would:

1. Violate the wire freeze (new reserved tag).
2. Duplicate the existing event's content.
3. Create a parallel audit channel the protocol spec doesn't recognize.

Therefore the design *names* the existing `campfire:compact` event as the audit record (§2.5) and pins its contents. Downstream impl tests look for the `campfire:compact` tag, not `compact:performed` (R7 explicitly enshrines this).

## Appendix B — Why we did not change the leaf filename format

The leaf is still `<19-digit-nanos>-<message-id>.cbor`. We considered shortening (drop the nanos prefix, rely on the day-bucket's residents being intra-day-orderable by content). Rejected: the in-bucket lex-sort of leaf filenames is what gives `ListMessages` its total order property without parsing CBOR. Removing the nanos prefix would force `ListMessages` to either decode every CBOR to sort by `Message.Timestamp` (slow) or rely on inode-mtime (unreliable across filesystems and rsync). The nanos prefix is small and load-bearing. Keep it.

## Appendix C — Windows deployment caveat (campfireagent-22d)

On Windows, flock(2) is not available. The migration lockfile discipline (§3.2) is implemented as a no-op on Windows: `cf migrate-store` acquires no exclusive lock, and `WriteMessage` does not acquire a shared lock. This is an acceptable degraded mode because:

1. **Windows is not a v0.3x deployment target.** Production instances run on Linux/macOS. Windows is primarily a developer machine platform.
2. **Migration race risk is bounded.** Concurrent writes during migration may cause messages to land in inconsistent buckets (some in the flat layout, some in the new layout), but the dual-read in §3.4 handles mixed-layout stores safely. Data loss does not occur; operators can re-run migration to clean up.
3. **Manual coordination is the workaround.** The `cf migrate-store` command prints a startup warning on Windows asking operators to stop all cf processes before running migration.

When a named Windows deployment need arises, implement full locking via `LockFileEx` (Windows-native equivalent of flock). See `cf-protocol/internal/transport/fs/lock_windows.go` for the no-op stub and future extension point.
